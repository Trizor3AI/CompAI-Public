# Cosmic Mission Log observations

Checked on 2026-10-26 against the installed development assemblies and public game sheets. This reader returns only positively observed Silver or Gold medals from the displayed, manually opened Mission Log. It is not a global completion catalogue. Missing medals, filtered rows, other jobs and other planets are unknown. No normal quests, mission availability, score, rewards, current mission actions or negative medal statuses are returned.

## Primary mappings

- [AgentWKSMission at b72bc1f](https://github.com/aers/FFXIVClientStructs/blob/b72bc1f73e5f2b09ba460a9238fbf3b9a5bbeb3c/FFXIVClientStructs/FFXIV/Client/UI/Agent/AgentWKSMission.cs) defines the typed MissionData pointer, IsMissionLog, selection fields, UpdateFlags, MissionList vector and MissionEntry records. Its MissionFlags explicitly names Silver and Gold. The installed assembly exposes these same fields and flags.
- [ECommons WKSMission at 00693e9](https://github.com/NightmareXIV/ECommons/blob/00693e92b52d067250f1724e362b5e88e3fdf365/ECommons/UIHelpers/AddonMasterImplementations/WKSMission.cs) documents displayed count at AtkValue 33, mission IDs at 36 + row * 6, and names at 802 + row * 2. A zero ID denotes a category header. Its callbacks and selection/start methods are not copied or called.
- [WKSManager at b72bc1f](https://github.com/aers/FFXIVClientStructs/blob/b72bc1f73e5f2b09ba460a9238fbf3b9a5bbeb3c/FFXIVClientStructs/FFXIV/Client/Game/WKS/WKSManager.cs) documents IsLoaded, TerritoryId and CurrentPlanetIndex. They guard the observation's lifetime, not the planet represented by the log.
- [StdVector](https://github.com/aers/FFXIVClientStructs/blob/b72bc1f73e5f2b09ba460a9238fbf3b9a5bbeb3c/FFXIVClientStructs/STD/StdVector.cs) and its [default wrapper](https://github.com/aers/FFXIVClientStructs/blob/b72bc1f73e5f2b09ba460a9238fbf3b9a5bbeb3c/FFXIVClientStructs/STD/StdVector.Default.cs) expose typed First/Last/End bounds. The reader does not invoke vector mutation methods.
- A [primary consumer's selection code](https://github.com/LeontopodiumNivale14/Ices-Cosmic-Exploration/blob/452e3a721a63297e1644e0ce6da4f07f2e96a46a/ICE/Utilities/Cosmic_Helper/AgentWKSMissionEx.cs) sets UpdateFlags when changing the selected job. This supports rejecting nonzero update flags. Zero alone is not treated as population or server-freshness proof: the reader also requires nonempty stable native/display lists and complete displayed ID/name/public-job correspondence.

## Installed and offline corroboration

An offline probe inspected installed managed metadata and local public WKSMissionUnit, ClassJob and ClassJobCategory definitions. The installed public catalogue contained 1,699 named mission rows, with LevelGroup values 1–6; EX and EX+ appear in some public names. The reader preserves public names and does not invent S/S+ labels or infer a medal from a tier.

The exact public GetMissionLog signature matched once in the on-disk game executable (SHA256 `46A52AB1DBE80B9A8D6C4D4531BF66693904200C5135FACACD053EF28A5DE14A`). Read-only disassembly showed that this builder writes **ClassJob IDs 8–18** into MissionEntry.ClassJobIndex, despite the field's name, and writes the explicit Silver/Gold enum values for positive medals. Production still requires membership in the actual public mission ClassJobCategory; it never invokes GetMissionLog, JobIndexToClassJobId, completion helpers or any state-populating function. No private field offset from this inspection is used by the reader.

That same inspection showed the Mission Log can select a planet separately from the player's current planet through private tab fields. Public mission PlaceName is zero for many rows; a [primary territory resolver](https://github.com/LeontopodiumNivale14/Ices-Cosmic-Exploration/blob/452e3a721a63297e1644e0ce6da4f07f2e96a46a/ICE/Utilities/Cosmic_Helper/CosmicTerritoryResolver.cs) falls back to manually maintained ID bands in that case. This reader uses neither private tab bytes nor ID-band guesses. **Its DTO deliberately contains no territory or planet attribution.** The current-zone manager check must not be described as proving mission-planet scope.

Private reproducible probe sources/output are under `.test-tmp/research-0500/cosmic`; those are not plugin runtime dependencies.

## Capture contract

- Framework-thread caller; separate permission and character/session/cache controls belong to the integration.
- Loaded player with nonzero ContentId; loaded WKSManager matching the caller's territory; stable current planet, player and manager identity.
- Exact active/ready/shown AgentWKSMission and its Rapture-owned, visible/ready WKSMission addon, with matching IDs and native/Dalamud handles. IsMissionLog must be true, UpdateFlags zero, and the selected job index supported.
- Positive typed vector addresses, pointer-size-aligned base, ordered element-aligned bounds and a defensive capacity cap of 512 entries. This cap is an acceptance policy, not a claim about the native allocation limit.
- Nonnull AtkValues with 803–4,096 entries; every indexed slot must be inside the actual buffer. Displayed count must be 1–128. The 128-row defensive cap keeps ID slots before the documented name region and bounds capture work; it includes category headers.
- Every non-header displayed mission must uniquely match a native entry and its public class-job membership. Native MissionUnitId is a uint; the reader explicitly accepts only 1–65,535 for the shared reference contract. Exact public/display title matching is required except for literal `???` rows without Silver or Gold, which are omitted after identity validation. Their public definitions and repeated samples still must remain stable. Missing definitions, duplicate IDs, conflicting Silver+Gold flags, unsupported job IDs, malformed text and all other public/display disagreement reject the observation.
- Mission names use bounded, terminated UTF-8/SeString copies with validated payloads and stable pointer/type/content checks. Result names preserve exact public text. `JobName + ": " + Name` must fit the shared 128-character result limit.
- Two complete samples, repeated owner checks and stable public-sheet/language references are required. Results are detached records in a read-only collection. A populated verified log with no positive medals produces an available empty collection; an empty/uninitialized or header-only log is unavailable. Neither case proves the user lacks medals.

## Validation limits

Version 0.53.0 leaves this native per-view reader unchanged and adds bounded integration retention in `ActivityObservationCache`. Positive observations merge by `(MissionUnitId, ClassJobId)` across stable views; selected-planet mapping remains unverified and is intentionally absent, as accepted by the user. Each entry expires fifteen minutes after its own observation, with a 512-entry oldest-first bound. Frozen results reindex detached rows and use the oldest included timestamp for conservative request expiry. `ActivityCache.Tests/CosmicAccumulationChecks.cs` covers view changes, individual expiry, stable sampling, immutable freezes, cap eviction, empty/unavailable views and reset behavior. The native 128-displayed-row guard remains separate from the 512 accumulated-entry cap.

The focused console fixture links the production reader against the installed Dalamud/ClientStructs/Lumina assemblies. It covers native allocations, visible-list correspondence, bounds, update/mode/owner/planet changes, exact public names/jobs, positive-only filtering, stale samples, immutable output and invalid text. These are synthetic checks, not an in-game comparison. The actual Mission Log must still be compared on a known Silver/Gold row, with job/filter/planet changes and menu closure. Caller retention and permission behavior require their separate integration checks.

## 0.52.2 failure diagnostics

`LastCaptureStatus` is an immutable, bounded first-failure report. It distinguishes owner/readiness, bounds, copy, native/display/public mapping, name mismatch and post-copy instability. It contains counts, selection/update values, an offending public mission ID/job/flags and boolean name-match/placeholder evidence only. It does not contain native addresses, character/account identity, displayed text, public mission titles or exception messages. Rejected vector capacities are calculated without dereferencing the rejected allocation.

The reported live Gold rows appeared beside hidden `???` rows. The 0.52.2 diagnostic confirmed a name-match rejection on a placeholder with no medal flags. In 0.52.3 this narrow omission-only case no longer suppresses readable medals. Fixtures use the reported flag combination1056, reject medal-bearing placeholders, preserve public mapping/stability checks and exclude hidden names from results. The full corrected log still needs an in-game comparison; the diagnostic proves the original rejection, not that every subsequent row will validate.
